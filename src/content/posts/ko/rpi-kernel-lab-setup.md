리눅스 커널에 패치를 보내보고 싶었다.

일단 코드를 수정하고 빌드한 다음, 실제 보드에서 돌려볼 환경이 필요했다. 가지고 있는 Raspberry Pi 5를 쓰면 되겠다고 생각했다. Raspberry Pi OS도 잘 돌아가고 있으니 커널만 직접 빌드해서 바꾸면 되지 않을까.

…여기서부터 생각보다 오래 걸렸다.

## 최대한 upstream에 가깝게

처음부터 Raspberry Pi 전용 커널에서 작업하고 싶지는 않았다. 내가 패치를 보낼 대상은 upstream Linux니까, 테스트하는 환경도 가능하면 거기에 가까웠으면 했다.

그래서 upstream 커널을 빌드해서 올려봤다. `Image`를 넣고, 같은 소스에서 빌드한 DTB도 넣고, 부팅 설정을 바꿨다.

안 뜬다.

정확히는, 그때는 안 뜨는 줄 알았다.

Raspberry Pi OS에서는 되던 것들이 커널과 DTB를 바꾸고 나면 그대로 동작하지 않았다. 설정을 더 찾아서 넣다 보면 이번에는 그 설정이 Raspberry Pi 쪽 커널과 DTB를 전제로 한 것이었다.

그럼 다시 어디까지 가져와야 하는지 고민하게 된다.

전용 커널을 그대로 쓰자니 원래 하고 싶던 환경과 멀어지고, upstream에 가깝게 가자니 보드에서 필요한 기능을 하나씩 확인해야 했다. “Pi 5 지원”이라는 말만으로는 부족했다. 내가 쓰려는 UART까지 되는 건지, 네트워크는 어떤지, 어떤 DTB와 설정을 썼는지까지 봐야 했다.

커널 패치를 해보려고 했는데 아직 테스트 환경을 만드는 중이다. 하..

## UART부터 연결

부팅 로그를 보려고 가지고 있던 Sipeed RV-Debugger Plus를 꺼냈다.

Pi 5에는 전용 디버그 UART 커넥터가 있다. 그런데 그 커넥터에 맞는 케이블이 없었다. 있는 건 점퍼선뿐이었다.

그래서 40핀 GPIO 헤더를 사용했다.

```text
RPi 5                         Sipeed
물리 8번  / GPIO14 / TX  ────  RX
물리 10번 / GPIO15 / RX  ────  TX
물리 6번  / GND          ────  GND
```

8번이 TX인지 RX인지도 다시 확인했다. GPIO 번호와 물리 핀 번호가 섞여 나오면 간단한 연결도 괜히 한 번 더 보게 된다.

Pi 전원은 별도로 공급하고, UART 쪽은 TX·RX·GND만 연결했다.

연결하고 설정을 바꾸니 로그가 나오기 시작했다.

```text
Loading 'Image' to 0x00000000 offset 0x200000
Read Image bytes 42772992 hnd 0x7ddc6
Device tree loaded to 0x2eff9100 (size 0x6e93)
```

그리고 끝.

응? 왜 여기까지 나오고 아무것도 안 나오지?

파일은 읽은 것 같고 DTB도 올린 것 같은데, 그 다음을 알 수가 없었다. 커널이 죽은 건지, 설정이 잘못된 건지, 내가 엉뚱한 UART를 보고 있는 건지.

GCC로 다시 빌드해봐도 비슷했다. `earlycon`도 보고, `console=`도 바꾸고, DTB도 의심했다. 바꿀 수 있는 게 많다는 것이 이럴 때는 별로 도움이 안 됐다.

## …HDMI는 나오네?

나중에 Debian 이미지를 시험하면서 HDMI를 확인했다.

화면이 나온다.

UART는 조용한데 HDMI에는 로그인 프롬프트가 떠 있었다.

```text
localhost login:
```

잠깐. 그럼 지금 부팅은 된 거잖아?

이때 좀 허탈했다. 나는 UART 출력이 끊기는 걸 보면서 계속 부팅 실패라고 생각하고 있었다. 그런데 적어도 이 Debian 이미지에서는 시스템이 로그인 화면까지 올라오고 있었다.

그동안 시험한 것도 전부 UART만 안 됐던 건가 싶었다. 물론 그건 아직 모른다. 이전 커널들을 같은 조건에서 다시 확인한 것은 아니니까.

그래도 실험을 보는 기준은 바뀌었다. 이후에는 “안 됨”이라고만 적으면 안 되겠다.

```text
HDMI: 로그인 화면 나옴
GPIO UART: 펌웨어 로그 이후 출력 없음
직접 빌드한 커널: 별도 검증 필요
```

이렇게 적어야 했다.

특히 내가 연결한 GPIO UART로 펌웨어 로그가 나온다는 것과, Linux 콘솔까지 같은 곳으로 나온다는 것은 따로 확인할 일이었다. 앞부분에 글자가 보이니까 배선과 콘솔 설정이 모두 끝났다고 생각한 게 문제였다.

## SD 카드를 언제까지 뽑아야 하나

중간부터는 다른 것도 귀찮아졌다.

빌드한 파일을 넣고, SD 카드를 Pi에 꽂고, 테스트하고, 다시 빼서 파일을 바꾸는 과정이다. 한두 번이면 괜찮다. 그런데 설정 하나 바꿀 때마다 반복하려니 흐름이 계속 끊겼다.

나는 앞으로 커널을 계속 바꾸려고 이걸 세팅하는 건데.

U-Boot를 쓰는 방법도 찾아봤고, 무선으로 할 수 있는지도 봤다. `kexec`도 생각했지만 당시 안정용 커널에서는 기능이 켜져 있지 않았다. 정상 설정을 보존하고 다음 한 번만 다른 커널로 부팅하는 `tryboot` 쪽도 검토했다.

여러 번 고민한 끝에, 내가 원하는 연결은 결국 이쪽으로 정리됐다.

```text
개발 PC
  │
  ├── USB ── Sipeed ── UART ── RPi 5
  │
  └──────── Ethernet ────────── RPi 5
```

**UART와 Ethernet을 둘 다 PC에 직접 연결하는 구성.**

UART에서는 로그를 보고, Ethernet으로는 정상 부팅한 Pi에 접속해서 파일을 옮긴다. 커널 이미지 전송까지 UART로 해결하려고 할 필요는 없었다.

처음에는 무선이면 더 편할 것 같았다. 그런데 커널을 바꿔가며 시험하는 동안 Wi-Fi까지 신경 쓰고 싶지는 않았다. 일단 유선으로 연결해두고, SSH와 파일 전송이 되는 기준 환경을 확보하는 게 내 목적에는 더 맞겠다고 생각했다.

물론 선을 꽂는다고 끝은 아니다. PC와 Pi 사이의 IP 설정이 필요하고, 테스트 커널에서 Ethernet이 실제로 동작하는지도 확인해야 한다. 네트워크가 올라오기 전에 커널이 멈추면 SSH는 사용할 수 없다. 그래서 UART도 같이 두는 것이다.

완전히 멈춘 보드를 리셋하는 문제는 또 남아 있다. 여기까지 자동화됐다고 말할 단계는 아니다.

## 이제는 정상 환경을 먼저 남겨두려고 한다

이번에 가장 아쉬웠던 건 비교 기준을 충분히 잡아두지 않고 이것저것 바꾼 것이다.

커널도 바뀌고 DTB도 바뀌고 부팅 옵션도 바뀌었다. 출력이 없으면 다시 다른 설정을 찾았다. 그러다 보니 지금 무엇 때문에 안 되는지 설명하기 어려워졌다.

당장은 다음 순서로 가려고 한다.

- 정상 부팅되는 환경을 보존한다.
- UART 출력과 Ethernet 접속 상태를 각각 확인한다.
- 그 환경의 커널 소스와 설정으로 직접 빌드해본다.
- 직접 빌드한 커널도 부팅되는지 확인한다.
- 그 다음 필요한 UART 변경이나 내가 테스트할 패치를 넣는다.

Upstream에 패치를 보내려는 목적은 그대로다. 다만 보드를 동작시키는 데 필요한 변경과 내가 보내려는 패치는 구분해서 관리하고 싶다.

아직 GPIO UART 문제를 다 해결한 것도 아니고, 원하는 개발 환경이 완성된 것도 아니다. 그래도 이제 어떤 환경을 만들어야 하는지는 조금 명확해졌다.

커널을 바꿔도 로그를 볼 수 있고, 새 파일을 쉽게 넣을 수 있고, 실패하면 정상 환경으로 돌아올 수 있는 것.

일단 여기까지 만들어놓고 싶다. 다음 빌드에서는 SD 카드부터 찾지 않게.
